What breaks when the traffic arrives

Executive summary

MUNI is two codebases wearing one name. The platform layer — API gateway resilience, RabbitMQ topology, Elasticsearch analyzers, Kubernetes manifests, the inventory reservation engine — is genuinely well-built, in places better than what most teams ship. The commerce layer underneath it is scaffolding: checkout, payment, escrow, payouts, loyalty and 22 other services hold their entire state in process-local JavaScript Maps and arrays that vanish on restart and are invisible to a second replica.

The single most urgent item is not a scale problem. The API gateway stamps x-user-id and x-user-roles onto requests from a verified JWT but never strips those headers when a client sends them directly, and every downstream service trusts them by design. Any anonymous caller can become ROLE_SUPER_ADMIN with two curl headers. That is a full authentication and authorization bypass, reachable today, on every route in the system.

Behind that, the checkout saga is a stub that calls an inventory endpoint which does not exist, swallows the failure, marks the step complete, and computes the order total from a client-supplied subtotal. There is no idempotency check anywhere in the money path, while the gateway retries failed POSTs three times. Black Friday is not the risk here — the first real customer is.

The good news is that the hard parts are largely done. The inventory service already implements correct SELECT … FOR UPDATE reservation with TTL expiry; the RabbitMQ layer already has retry, DLQ and Redis idempotency; the search service already has edge-ngram autocomplete. Most of the critical work is connecting these to the commerce path, not inventing them. Realistic path to a safe launch: 2 weeks for the critical set, 6–8 weeks to the full standard.

Critical — must fix before any deployment

These are not "will degrade at scale" items. Each one is exploitable or loses money on day one at ten requests per second.

C1 Auth & RBAC API Gateway 4 hours

Client-supplied identity headers are trusted — complete auth bypass

backend/api-gateway/src/middleware/auth.middleware.ts:27–58 · src/utils/proxy.ts:91–95

Current state
optionalAuth sets x-user-id / x-user-roles only when a JWT verifies. It never deletes them otherwise. requireAuth then short-circuits on line 40 — if (req.headers['x-user-id']) return next() — and requireRole reads roles straight off the same header. callUpstream copies every inbound header to the service verbatim. The design note at line 22 states services deliberately do not re-validate the JWT.
Failure scenario
No load required. This request returns the full customer database:
curl https://api.muni.ug/api/v1/admin/users \
  -H "x-user-id: 00000000-0000-0000-0000-000000000000" \
  -H "x-user-roles: ROLE_SUPER_ADMIN"

The same two headers let an attacker read any user's orders, confirm any checkout session, approve seller KYC, and — because the rate limiter also keys on x-user-id (rate-limit.middleware.ts:85) — bypass rate limiting entirely by rotating a random UUID per request. The Kubernetes NetworkPolicy does not help: the traffic arrives through the gateway, which forwards it.

The fix

Strip the headers unconditionally before anything else reads them, and stop treating their presence as proof of authentication.

// backend/api-gateway/src/middleware/auth.middleware.ts

// Runs FIRST in the middleware chain — before logging, rate-limit, routes.
const SPOOFABLE = ['x-user-id', 'x-user-roles', 'x-user-email', 'x-internal-call'];

export function stripClientIdentity(req, _res, next) {
  for (const h of SPOOFABLE) delete req.headers[h];
  next();
}

export function optionalAuth(req, _res, next) {
  const identity = readAccessToken(
    req.header('authorization')?.replace(/^Bearer\s+/i, ''),
  );
  if (identity) {
    req.headers['x-user-id']    = identity.sub;
    req.headers['x-user-roles'] = identity.roles.join(',');
  }
  next();
}

export function requireAuth(req, res, next) {
- if (req.headers['x-user-id']) return next();   // ← trusts the client
+ // optionalAuth already ran on a stripped request, so the header
+ // is now present only if a JWT actually verified.
+ if (req.headers['x-user-id']) return next();
  return res.status(401).json({ /* … */ });
}
// backend/api-gateway/src/app.ts — order matters
app.use(express.json({ limit: '2mb' }));
+ app.use(stripClientIdentity);   // ① before ANY consumer of the headers
app.use(loggingMiddleware);
app.use(responseTransformer);
app.use(optionalAuth);
app.use(metricsMiddleware);
app.use(rateLimiter());

Then add defence in depth, because a single stripped header should not be the only thing between the internet and ROLE_SUPER_ADMIN: sign the identity hop. The gateway mints a short-lived internal assertion; services verify it.

// backend/shared/utils/internal-identity.ts (new)
import jwt from 'jsonwebtoken';
const SECRET = process.env.INTERNAL_IDENTITY_SECRET!;   // no dev fallback

export const signIdentity = (sub: string, roles: string[]) =>
  jwt.sign({ sub, roles }, SECRET, { expiresIn: '30s', issuer: 'api-gateway' });

export function verifyIdentity(token?: string) {
  if (!token) return null;
  try { return jwt.verify(token, SECRET, { issuer: 'api-gateway' }) as
    { sub: string; roles: string[] }; }
  catch { return null; }
}

C2 Checkout Saga 3–4 days

The checkout saga reserves nothing and charges nothing

backend/services/checkout-service/src/services/checkout.service.ts:36–86

Current state
Three separate defects compound:
  • The reserve call posts to ${invUrl}/api/v1/inventory/reserve. The inventory service only routes /api/v1/inventory/:variantId/reserve (inventory-service/src/index.ts:76), so this always 404s. A 404 does not throw in fetch, so the catch never fires and line 42 marks RESERVE_INVENTORY as completed.
  • It sends { items: [] } — the cart contents are never transmitted.
  • confirmPayment (line 58) never contacts payment-service. It flips status to PAYMENT_CONFIRMED and fabricates an order id. No money moves; no deduct is ever called.
Failure scenario
A flash sale on 50 units sells unbounded quantity — the reservation that would have blocked it silently no-ops. Every order reaches COMPLETED with zero payment collected, and fulfilment ships against stock that does not exist. There is also no compensating action anywhere: cancelCheckout sets a status string and releases nothing.

The fix

A real orchestrated saga with an explicit compensation stack. Each step registers its undo before the next step runs.

// backend/services/checkout-service/src/saga/checkout.saga.ts (new)

type Compensation = () => Promise<void>;

export async function runCheckoutSaga(session: CheckoutSession) {
  const undo: Compensation[] = [];

  try {
    // ── 1. Price the cart SERVER-SIDE (never trust client totals) ──
    const priced = await pricing.priceCart(session.userId, session.cartId);
    session.subtotal = priced.subtotal;
    session.total    = priced.total;

    // ── 2. Reserve every line, one call per variant ──
    for (const line of priced.items) {
      const r = await http.post(
        `${INVENTORY_URL}/api/v1/inventory/${line.variantId}/reserve`,
        { quantity: line.quantity, sessionId: session.id, userId: session.userId },
      );
      if (r.status === 409) throw new OutOfStockError(line.variantId);
      if (!r.ok)            throw new StepFailedError('RESERVE_INVENTORY');

      const reservationId = r.data.reservationId;
      undo.push(() => http.post(
        `${INVENTORY_URL}/api/v1/inventory/${line.variantId}/release`,
        { reservationId },
      ));
    }

    // ── 3. Charge, keyed to the session so a retry cannot double-charge ──
    const payment = await http.post(`${PAYMENT_URL}/api/v1/payments`, {
      orderId:        session.id,
      amount:         session.total,
      currency:       priced.currency,
      method:         session.paymentMethod,
      idempotencyKey: `checkout:${session.id}`,          // ← see C4
    });
    if (!payment.ok) throw new StepFailedError('PAYMENT');
    undo.push(() => http.post(`${PAYMENT_URL}/api/v1/payments/${payment.data.paymentId}/refund`));

    // ── 4. Create the order, then deduct against the reservations ──
    const order = await http.post(`${ORDER_URL}/api/v1/orders`, {
      userId: session.userId, items: priced.items, total: session.total,
      idempotencyKey: `order:${session.id}`,
    });
    if (!order.ok) throw new StepFailedError('CREATE_ORDER');

    for (const line of priced.items) {
      await http.post(`${INVENTORY_URL}/api/v1/inventory/${line.variantId}/deduct`,
        { quantity: line.quantity, reservationId: line.reservationId });
    }

    session.status  = 'COMPLETED';
    session.orderId = order.data.id;
    return session;

  } catch (err) {
    // Compensate in reverse order; never let an undo failure mask the cause.
    for (const step of undo.reverse()) {
      await step().catch((e) => logger.error('compensation failed', {
        sessionId: session.id, error: e.message,
      }));
    }
    session.status        = 'FAILED';
    session.failureReason = (err as Error).message;
    throw err;
  }
}

Reservations already expire on their own — InventoryReservation.expiresAt is indexed and expiry.worker.ts sweeps them — so a crashed orchestrator self-heals after the 15-minute TTL. Enable that worker; it is currently commented out at inventory-service/src/index.ts:9.

C3 Checkout Pricing 4 hours

The customer sets their own price

backend/services/checkout-service/src/services/checkout.service.ts:23, 32–34

Current state
subtotal: data.subtotal || 100 takes the subtotal straight from the request body. Shipping and tax are hardcoded to 10 and 5. The total the customer pays is whatever they posted.
Failure scenario
POST /api/v1/checkout/initiate with {"subtotal": 1} buys anything in the catalogue for 16 currency units. No load, no race, no timing — one request. This will be found by the first person who opens devtools.
The fix

C4 Idempotency Payments 1–2 days

No idempotency in the money path — while the gateway retries POSTs three times

backend/services/payment-service/src/services/gateway.service.ts:91 · backend/api-gateway/src/utils/proxy.ts:65–72

Current state
idempotencyKey is accepted by the payment controller and written onto the transaction object — and never read again. There is no lookup, no store, no uniqueness constraint. Meanwhile the gateway wraps every request, including POST /checkout and POST /payments, in withRetry({ maxAttempts: 3 }) and treats any 5xx as retryable.
Failure scenario
Payment-service takes 9 seconds under load. The gateway's 8-second AbortController fires, the retry wrapper fires twice more — three MTN MoMo collection requests, three PIN prompts, three debits, one order. At 100,000 checkouts with a 2% timeout rate that is 2,000 customers double- or triple-charged, and every one of them is a chargeback plus a support ticket. The Redis idempotency guard that would prevent this already exists at infrastructure/rabbitmq/idempotency.ts — it is only wired into message consumers, not HTTP.

The fix — part 1: stop retrying non-idempotent methods

The fix — part 2: an idempotency middleware

Redis SET NX claims the key; the completed response is written back under the same key so a replay returns the original result rather than re-executing.

// backend/shared/http/idempotency.middleware.ts (new)
import { createHash } from 'node:crypto';

const TTL_SEC     = 24 * 60 * 60;   // 24h — outlives any client retry window
const IN_FLIGHT   = 'IN_FLIGHT';

export function idempotent(redis: RedisClient) {
  return async (req, res, next) => {
    const raw = req.header('idempotency-key');
    if (!raw) return res.status(400).json({
      error: { code: 'IDEMPOTENCY_KEY_REQUIRED',
               message: 'Send an Idempotency-Key header with this request.' } });

    // Scope to the user so key collisions across accounts are impossible.
    const key  = `idem:${req.headers['x-user-id']}:${raw}`;
    // Fingerprint the body: same key + different body = client bug, not a retry.
    const hash = createHash('sha256').update(JSON.stringify(req.body)).digest('hex');

    const claimed = await redis.set(key, `${IN_FLIGHT}:${hash}`, { NX: true, EX: TTL_SEC });

    if (!claimed) {
      const stored = await redis.get(key);
      const [state, storedHash] = stored!.split(/:(.+)/);

      if (state === IN_FLIGHT) {
        if (storedHash !== hash) return res.status(422).json({
          error: { code: 'IDEMPOTENCY_KEY_REUSED',
                   message: 'This key was already used with a different request body.' } });
        res.setHeader('Retry-After', '2');
        return res.status(409).json({
          error: { code: 'REQUEST_IN_PROGRESS',
                   message: 'The original request is still processing. Retry shortly.' } });
      }
      // Completed — replay the stored response verbatim.
      const done = JSON.parse(stored!.slice(state.length + 1));
      res.setHeader('Idempotent-Replay', 'true');
      return res.status(done.status).json(done.body);
    }

    // First caller: capture the response so replays can be served from it.
    const json = res.json.bind(res);
    res.json = (body) => {
      if (res.statusCode < 500) {
        redis.set(key, `DONE:${JSON.stringify({ status: res.statusCode, body })}`,
                  { EX: TTL_SEC }).catch(() => {});
      } else {
        redis.del(key).catch(() => {});   // 5xx: let the client genuinely retry
      }
      return json(body);
    };
    next();
  };
}
// Apply to every state-changing money route.
router.post('/checkout/initiate',        requireAuth, idempotent(redis), initiateCheckout);
router.post('/checkout/:id/confirm',     requireAuth, idempotent(redis), confirmPayment);
router.post('/api/v1/payments',          requireAuth, idempotent(redis), initiatePayment);

Load headroom: at 100,000 checkouts these are two Redis round-trips each — roughly 200k ops against a store that handles millions per second. The idempotency layer is not the bottleneck; set maxmemory-policy noeviction on that Redis so keys are never evicted early, and give it its own instance separate from the cache.

Separately, pass the key through to the provider. mtn-momo.driver.ts and airtel-money.driver.ts should send X-Reference-Id derived from the stable reference, not a fresh crypto.randomBytes per attempt (gateway.service.ts:57).

C5 Persistence Scalability 3–4 weeks

26 of 32 services have no database — including every service that touches money

checkout.service.ts:5 · payment-service/src/services/{escrow,split,payout}.service.ts · +23 more

Current state
Only auth, user, product, container, order and inventory persist anything. Everything else uses module-level state. The money-critical ones:
  • checkout.service.ts:5 — const sessions: CheckoutSession[] = []
  • payment/escrow.service.ts:5 — the escrow ledger, in a Map
  • payment/split.service.ts:9–11 — vendor balances, ledger entries, platform commissions
  • payment/payout.service.ts:11 — vendor payouts
  • payment/index.ts:11 and consumers/order.consumer.ts:12 — payments and payment intents
Failure scenario
Three independent failures, and the HPA guarantees all three. (a) minReplicas: 2 means a customer who initiates checkout on pod A and confirms on pod B gets 404 Session not found — roughly half of all checkouts fail immediately. (b) Any restart, rollout or OOM-kill erases every in-flight order, the entire escrow ledger and all unpaid vendor balances, with no recovery path. (c) sessions is an array that is only ever pushed to — a slow memory leak that ends in an OOM-kill, which triggers (b).
The fix
Triage rather than boil the ocean. Tier 1 (must persist before launch): checkout, payment, escrow, split, payout, fulfillment, dispute, return, loyalty. Tier 2 (can stay ephemeral briefly): pricing, advertising, qa, container, fraud. Tier 3 (legitimately ephemeral): chat presence, analytics counters — these already have a Redis fallback and derive from event streams.

Checkout sessions specifically belong in Redis, not Postgres — they are short-lived, TTL-bounded, and read once:

// backend/services/checkout-service/src/repositories/session.repository.ts (new)
const TTL_SEC = 15 * 60;                        // mirrors the reservation TTL
const key = (id: string) => `checkout:session:${id}`;

export const sessionRepo = {
  async save(s: CheckoutSession) {
    await redis.setEx(key(s.id), TTL_SEC, JSON.stringify(s));
    // Secondary index so getHistory() never scans the keyspace.
    await redis.zAdd(`checkout:user:${s.userId}`, { score: Date.now(), value: s.id });
    await redis.expire(`checkout:user:${s.userId}`, TTL_SEC);
  },

  async find(id: string): Promise<CheckoutSession | null> {
    const raw = await redis.get(key(id));
    return raw ? JSON.parse(raw) : null;
  },
};

// Completed sessions get written to Postgres/Mongo as an immutable audit record;
// the Redis copy is allowed to expire.

Escrow, splits and payouts are financial records and need a real ledger table with an append-only shape and a monetary type — DECIMAL/BIGINT minor units, never JavaScript number, which loses precision above 253 UGX minor units.

C6 Authorization IDOR 3 hours

Any logged-in user can read and confirm any other user's checkout

backend/services/checkout-service/src/controllers/checkout.controller.ts:11–29

Current state
getSession, confirmPayment and cancelCheckout look the session up by req.params.sessionId and return or mutate it. None of them compares session.userId to res.locals.userId. requireAuth proves the caller is a user, not the user.
Failure scenario
Session ids are UUIDv4 so they are not guessable by brute force — but they leak through logs, referrer headers, support tickets and the browser history of a shared device. Given one, an attacker reads the victim's full cart, shipping address and phone number, and can cancel their order mid-purchase. Combined with C1, no login is needed at all.
The fix
Ownership checks belong in the service layer, not the controller, so no future caller can skip them.
// checkout.service.ts — take the actor on every read/mutate
async getSession(id: string, actorId: string, actorRoles: string[]) {
  const s = await sessionRepo.find(id);
  if (!s) throw new NotFoundError('Checkout session not found');

  const isOwner = s.userId === actorId;
  const isStaff = actorRoles.includes('ROLE_ADMIN') || actorRoles.includes('ROLE_SUPER_ADMIN');

  // 404 rather than 403 — a 403 confirms the id exists.
  if (!isOwner && !isStaff) throw new NotFoundError('Checkout session not found');
  return s;
}

Audit the same pattern across order-service, payment-service, return-service and dispute-service — every findById reached from an HTTP route needs the actor threaded through it.

C7 Auth Secrets 6 hours

JWT signing secrets fall back to a hardcoded string committed to the repo

backend/shared/utils/token.ts:11–14

Current state
process.env.JWT_ACCESS_SECRET ?? 'muni-dev-access-secret-change-me'. If the env var is missing or misspelled in any environment, the service starts happily and signs production tokens with a public string. Add a denylist so logout and account-disable take effect immediately. Keys expire on their own at token expiry, so the set stays small — at 15-minute tokens it holds only the last 15 minutes of revocations:

// Gateway checks this once per request; it is a single Redis EXISTS.
export async function isRevoked(jti: string) { return (await redis.exists(`revoked:${jti}`)) === 1; }
export async function revoke(jti: string, expUnix: number) {
  const ttl = Math.max(1, expUnix - Math.floor(Date.now() / 1000));
  await redis.setEx(`revoked:${jti}`, ttl, '1');
}

On the 100k-user CPU question: HS256 is HMAC-SHA256, roughly 5µs per verify — around 0.5% of one core at 1,000 rps. It is not your bottleneck and there are no public keys to cache. The real reason to move to RS256/EdDSA is not CPU, it is that a symmetric secret must be shared with every service that verifies it, so any one compromised service can mint admin tokens. With the C1 fix in place, only the gateway verifies, which makes HS256 defensible for now; plan the asymmetric migration for when you add a second verifier.

C8 MFA 1–2 days

TOTP is implemented but enforced nowhere, and its endpoints are unauthenticated

backend/services/auth-service/src/controllers/totp.controller.ts:8, 80 · src/app.ts:76–78 · src/services/auth.service.ts:116

Current state
The TOTP service, repository and Prisma model are all real and correct. But login() never consults them — it returns a full token pair on password alone, for admins included. The three 2FA routes are registered with no auth middleware, and generate2FASecret defaults the subject to a literal: (req.headers['x-user-id'] as string) || res.locals.userId || 'user-123'. authenticate2FA takes userId from the request body.
Failure scenario
Two things. Credential stuffing against /api/v1/auth/login reaches admin accounts with nothing but a leaked password — MFA exists in the database but is never checked. And because POST /api/v1/auth/2fa/generate is anonymous, an attacker can overwrite the stored secret for any user id they name, then use their own authenticator to satisfy a verification step you later add.

The fix

// auth.service.ts — split login into two steps when 2FA is on
export async function login(input: { email: string; password: string }, repo = userRepository) {
  const user = await repo.findByEmail(input.email);
  const ok = user ? await bcrypt.compare(input.password, user.passwordHash)
                  : (await bcrypt.hash('dummy', 4), false);
  if (!user || !ok)  throw Object.assign(new Error('Invalid email or password'), { status: 401 });
  if (!user.active)  throw Object.assign(new Error('Account is deactivated'),    { status: 403 });

  const twoFactor  = await twoFactorRepository.find(user.id);
  const isPrivileged = user.roles.some(r =>
    r === 'ROLE_ADMIN' || r === 'ROLE_SUPER_ADMIN' || r === 'ROLE_SELLER');

  // Admins and sellers MUST enrol — no grandfathering.
  if (isPrivileged && !twoFactor?.enabled) {
    return { status: 'MFA_ENROLLMENT_REQUIRED',
             enrollmentToken: createMfaChallengeToken(user.id, 'enrol') };
  }

  if (twoFactor?.enabled) {
    // A 5-minute single-purpose token. NOT an access token — carries no roles.
    return { status: 'MFA_REQUIRED',
             challengeToken: createMfaChallengeToken(user.id, 'verify') };
  }

  await repo.update(user.id, { lastLoginAt: new Date() });
  return buildAuthResponse(user, repo);
}

// POST /api/v1/auth/mfa/verify — exchange challengeToken + 6-digit code for tokens
export async function verifyMfa(challengeToken: string, code: string) {
  const claim = readMfaChallengeToken(challengeToken);       // throws if expired/wrong purpose
  if (!claim) throw Object.assign(new Error('Challenge expired — sign in again'), { status: 401 });

  // Rate-limit hard: 6 digits is 1M combinations, brute-forceable in minutes.
  const attempts = await redis.incr(`mfa:attempts:${claim.sub}`);
  if (attempts === 1) await redis.expire(`mfa:attempts:${claim.sub}`, 900);
  if (attempts > 5)   throw Object.assign(new Error('Too many attempts'), { status: 429 });

  const stored = await twoFactorRepository.find(claim.sub);
  if (!stored?.enabled || !TOTPService.verifyToken(stored.secret, code)) {
    throw Object.assign(new Error('Invalid verification code'), { status: 401 });
  }
  // Burn the code so a shoulder-surfed digit cannot be replayed inside its 30s window.
  const burned = await redis.set(`mfa:used:${claim.sub}:${code}`, '1', { NX: true, EX: 90 });
  if (!burned) throw Object.assign(new Error('Code already used'), { status: 401 });

  await redis.del(`mfa:attempts:${claim.sub}`);
  return buildAuthResponse(await userRepository.findById(claim.sub));
}
// auth-service/src/app.ts — these routes were completely open
- app.post('/api/v1/auth/2fa/generate', totpController.generate2FASecret);
- app.post('/api/v1/auth/2fa/verify',   totpController.verify2FASecret);
+ app.post('/api/v1/auth/2fa/generate', requireAuth, totpController.generate2FASecret);
+ app.post('/api/v1/auth/2fa/verify',   requireAuth, totpController.verify2FASecret);

C9 Rate limiting 1 day

The rate limiter can be bypassed with a header, and its fallback multiplies the limit by replica count

backend/api-gateway/src/middleware/rate-limit.middleware.ts:17, 46–51, 84–90

Current state
Four compounding problems. The key is rl:${userId ?? ip} where userId comes from the spoofable header (C1) — rotate a UUID per request and there is no limit. It is a fixed window, not the sliding window the comment claims, so a client gets 2× the limit across a boundary. One global bucket covers all endpoints, so /search and /checkout share a budget with /health. And fallbackStore is a per-process Map that is never pruned: with 20 gateway replicas the effective limit becomes 20× the configured value whenever Redis blips, while the map grows without bound.
Failure scenario
A scraper walks your catalogue at unlimited rate by sending a fresh x-user-id each request. During a Redis failover, 20 replicas each admit 100 rps per anonymous IP — 2,000 rps to product-service, which has no cache (H4) — and the fallback map accumulates one entry per distinct key until the pod is OOM-killed.

The fix

A real sliding-window counter in a single Lua round-trip, keyed on verified identity, with per-endpoint costs and a bounded local fallback.

// Sliding window log, atomic — one RTT instead of the current INCR + pTTL.
const SLIDING_WINDOW = `
  local key, now, window, limit = KEYS[1], tonumber(ARGV[1]), tonumber(ARGV[2]), tonumber(ARGV[3])
  redis.call('ZREMRANGEBYSCORE', key, 0, now - window)
  local count = redis.call('ZCARD', key)
  if count < limit then
    redis.call('ZADD', key, now, ARGV[4])      -- unique member per request
    redis.call('PEXPIRE', key, window)
    return {1, limit - count - 1}
  end
  return {0, 0}
`;

// Cost-weighted, so expensive endpoints drain the budget faster.
const COST: Array<[RegExp, number]> = [
  [/^\/api\/v1\/checkout/,  20],
  [/^\/api\/v1\/payments/,  20],
  [/^\/api\/v1\/search/,     5],
  [/^\/api\/v1\/auth\/login/, 10],   // credential stuffing brake
  [/^\/health/,              0],
];
export function rateLimiter(windowMs = 60_000) {
  return async (req, res, next) => {
    // x-user-id is now trustworthy only because stripClientIdentity ran first (C1).
    const userId = req.headers['x-user-id'] as string | undefined;
    const limit  = getLimitForRoles(req.headers['x-user-roles'] as string);
    const cost   = COST.find(([re]) => re.test(req.path))?.[1] ?? 1;
    if (cost === 0) return next();

    // Anonymous traffic keys on IP; authenticated keys on the verified subject.
    const key = `rl:${userId ?? `ip:${req.ip}`}`;

    let allowed: boolean, remaining: number;
    try {
      const [ok, rem] = await redis.eval(SLIDING_WINDOW, {
        keys: [key],
        arguments: [String(Date.now()), String(windowMs),
                    String(Math.floor(limit / cost)), randomUUID()],
      }) as [number, number];
      allowed = ok === 1; remaining = rem;
    } catch {
      // Redis down → local token bucket, sized to limit/replicaCount so the
      // fleet-wide total still approximates the intended ceiling.
      const perPod = Math.ceil(limit / Number(process.env.GATEWAY_REPLICAS ?? 1));
      ({ allowed, remaining } = localBucket.take(key, perPod, windowMs));
    }

    res.setHeader('X-RateLimit-Limit', limit);
    res.setHeader('X-RateLimit-Remaining', Math.max(0, remaining));

    if (!allowed) {
      const retry = Math.ceil(windowMs / 1000);
      res.setHeader('Retry-After', retry);
      return res.status(429).json({
        success: false, data: null,
        error: { code: 'RATE_LIMITED',
                 message: 'Too many requests. Please slow down.' },
        meta: { retryAfter: retry, timestamp: new Date().toISOString() },
      });
    }
    next();
  };
}

Back the local fallback with an LRU capped at ~10,000 entries rather than an unbounded Map — lru-cache with max: 10_000, ttl: windowMs gives you eviction for free. Note also that the current implementation returns a bare { message } on 429 while every other error returns the standard envelope; make it consistent so clients can parse one shape.

// backend/shared/http/validate.ts (new) — one middleware, applied everywhere
import type { ZodTypeAny } from 'zod';

export const validate = (schema: ZodTypeAny, source: 'body' | 'query' | 'params' = 'body') =>
  (req, res, next) => {
    const result = schema.safeParse(req[source]);
    if (!result.success) {
      return res.status(422).json({
        success: false, data: null,
        error: {
          code: 'VALIDATION_FAILED',
          message: 'Some fields need attention.',
          fields: result.error.issues.map(i => ({
            field: i.path.join('.') || source,
            message: i.message,
          })),
        },
        meta: { timestamp: new Date().toISOString() },
      });

H4Caching3–4 days

Product-service connects to Redis and never caches anything

product-service/src/app.ts:14,131 connects the cache · product.service.ts and category.service.ts never call it

The hottest read path in the system — product detail, category listings, homepage containers — goes to Postgres on every request. listProducts additionally runs a $transaction of findMany + count, so every page view is two queries plus a full COUNT(*) over the filtered set. cache.getOrSet is currently used only by analytics, chat and recommendation.

At 1M concurrent browsers this is millions of queries per minute against a single primary. The COUNT(*) alone will saturate it long before the reads do.

Cache-aside with stampede, penetration and herd protection

// backend/shared/cache/protected-cache.ts (new)
// The existing cache.getOrSet has none of the three protections below.

const NULL_SENTINEL = 'NULL';

export async function cached<T>(
  key: string, ttlSec: number, fetcher: () => Promise<T | null>,
): Promise<T | null> {

  const hit = await redis.get(key).catch(() => null);
  if (hit === NULL_SENTINEL) return null;                    // ① penetration
  if (hit !== null) return JSON.parse(hit) as T;

  // ② Stampede: exactly one caller computes; the rest wait briefly and re-read.
  const lock = `lock:${key}`;
  const got  = await redis.set(lock, '1', { NX: true, EX: 10 }).catch(() => 'OK');

  if (!got) {
    for (let i = 0; i < 20; i++) {                            // up to ~1s
      await sleep(50);
      const late = await redis.get(key).catch(() => null);
      if (late === NULL_SENTINEL) return null;
      if (late !== null) return JSON.parse(late) as T;
    }
    return fetcher();      // lock holder is slow — fall through rather than 504
  }

  try {
    const value = await fetcher();
    // ③ Herd: ±20% jitter so a million keys set together do not expire together.
    const jittered = Math.floor(ttlSec * (0.8 + Math.random() * 0.4));

    if (value === null) {
      await redis.setEx(key, 60, NULL_SENTINEL);              // short TTL for misses
    } else {
      await redis.setEx(key, jittered, JSON.stringify(value));
    }
    return value;
  } finally {
    await redis.del(lock).catch(() => {});
  }
}

On Redis being down: the existing cache.getOrSet already degrades correctly — it catches and calls the fetcher — so you fail open to the database. That is the right default for correctness but it means a Redis outage instantly moves 100% of read traffic onto Postgres. Pair it with a circuit breaker around the cache client and a small in-process LRU (a few thousand hot products, 5–10s TTL) so the database sees a fraction of that surge. You already have resilience/circuit-breaker.ts in the gateway — lift it into shared/ and reuse it.

For invalidation, use versioned keys rather than delPattern. The current delPattern runs SCAN across the keyspace, which is O(N) and slows linearly as the catalogue grows. Bump a per-entity version instead — product:v{n}:{id} — and stale keys expire on their own.

H5SearchIndexes1–2 days

Product search runs ILIKE '%q%' against Postgres while a tuned Elasticsearch index sits unused

product-service/src/services/product.service.ts:47–53

{ contains: params.q, mode: 'insensitive' } on both name and description compiles to ILIKE '%q%'. A leading wildcard cannot use a B-tree index, so this is a sequential scan of the entire product table on every keystroke, ORed across two columns and combined with a COUNT(*).

At 10 million products this is a multi-second scan per search. Under a flash sale it will hold connections until the pool is exhausted and every unrelated query — including inventory reservation — starts queueing behind it. This is the single most likely cause of a total site outage.

The frustrating part is that the fix is already built. search-service has custom edge_ngram analyzers, synonyms, vector query building and a product consumer keeping the index warm. It is simply not on the path that GET /api/v1/products?q= takes.

H7Concurrency2–3 days

Flash-sale hot rows will serialize on a single Postgres lock

inventory-service/src/index.ts:91–142

The reservation logic is correct — SELECT … FOR UPDATE inside a transaction, availability computed as stock - reserved, an expiring reservation row. Correctness is not the problem.

At 50,000 concurrent buyers on one variant, every transaction queues on the same row lock. Each holds it for a SELECT, an UPDATE, a conditional UPDATE … WHERE NOT EXISTS with three correlated subqueries, and an INSERT — call it 3–5ms. That caps you at roughly 200–300 reservations per second for that variant regardless of how many pods you run, and 49,000 connections pile up behind it until the pool and then the gateway's 8s timeout both blow. There is no deadlock risk on a single row, but there is once you reserve multiple variants per checkout — two carts holding overlapping variants in different orders will deadlock.

Three changes, in order of impact

// ① Always lock in a deterministic order. This alone removes multi-item deadlocks.
const ordered = [...items].sort((a, b) => a.variantId.localeCompare(b.variantId));
for (const item of ordered) { /* reserve */ }
-- ② Drop FOR UPDATE for a single conditional UPDATE. Same guarantee,
--    one statement, lock held for microseconds instead of milliseconds.
UPDATE "ProductVariant"
SET    reserved = reserved + $2, "updatedAt" = NOW()
WHERE  id = $1
  AND  stock - reserved >= $2      -- the check IS the lock
RETURNING stock - reserved AS remaining;
-- Zero rows affected ⇒ insufficient stock ⇒ 409. No read-then-write window.
-- Move the OUT_OF_STOCK product update out of this transaction and onto an event.
// ③ For announced flash sales, do not touch Postgres on the hot path at all.
// Pre-load the allocation into Redis; decrement atomically; settle to Postgres async.
const FLASH_RESERVE = `
  local remaining = tonumber(redis.call('GET', KEYS[1]) or '0')
  local want = tonumber(ARGV[1])
  if remaining >= want then
    redis.call('DECRBY', KEYS[1], want)
    redis.call('SETEX', KEYS[2], ARGV[2], want)   -- reservation token w/ TTL
    return 1
  end
  return 0
`;
// Single-key Lua on one Redis shard: ~100k ops/sec, no lock convoy.

On Redlock: you do not currently use distributed locks anywhere, and for inventory you should not start. Redlock's failure mode is exactly the one that costs money — a lock holder that pauses for GC past the TTL keeps operating while another client acquires the same lock, and you oversell. The atomic conditional UPDATE above needs no lock at all, which is strictly safer. Reserve Redlock for genuinely non-transactional coordination such as "only one pod runs the payout batch".

H8Auth4 hours

Refresh rotation runs a bcrypt compare per token in the family

auth-service/src/services/auth.service.ts:155–162

The rotation and reuse-detection logic is correct and well thought through — revoking the whole family on reuse is exactly right. The cost model is not: the loop bcrypt-compares the presented token against every unrevoked record in the family, at cost factor 10 (~100ms each). A family that accumulates n live tokens costs n × 100ms of blocked CPU per refresh.

At 100,000 users refreshing hourly — roughly 28 rps — even a single compare each saturates three cores. bcrypt is deliberately slow; it belongs on passwords, not on a token that is already 256 bits of entropy.

// Refresh tokens are high-entropy already — a plain SHA-256 is the right primitive.
// It also makes the lookup a single indexed query instead of a scan.
const hashToken = (raw: string) =>
  createHash('sha256').update(raw).digest('hex');

// prisma: @@unique([tokenHash])
const record = await repo.findRefreshTokenByHash(hashToken(rawToken));

if (!record || record.revokedAt || record.expiresAt < new Date()) {
  // Reuse detection is unchanged: a valid-signature token with no live
  // record means it was already rotated ⇒ revoke the family.
  const payload = readRefreshToken(rawToken);
  if (payload) await repo.revokeFamily(payload.family);
  throw Object.assign(new Error('Refresh token reuse detected — please log in again'),
                      { status: 401 });
}

Also replace the per-token revocation loop in logout (line 194) with a single updateMany on the family. And note bcryptjs is the pure-JS implementation — roughly 3–5× slower than native bcrypt and it blocks the event loop rather than using the thread pool. On the login path, where the cost factor is the point, switch to native bcrypt or argon2.

H9Domain design1–2 weeks

Synchronous REST chains where events belong

The domain decomposition itself is sound — Product, Inventory, Order, Payment, Fulfilment are properly separated, and inventory logic does not leak into order-service. The coupling problem is in the transport. Checkout calls inventory, payment and order over synchronous HTTP, so its availability is the product of theirs: four services at 99.9% each give the checkout path 99.6%, or about three hours of downtime a month, and one slow dependency stalls the whole chain.

The right split: synchronous for anything the customer must see resolved before the response — reserve, charge, create order. Asynchronous for everything downstream — notification, analytics, fulfilment, loyalty accrual, search reindex, seller payout. Several of these already consume events (inventory/consumers/order.consumer.ts, payment/consumers/order.consumer.ts, search/consumers/product.consumer.ts), so the pattern is established; it just is not applied consistently.

On the roadmap's 2PC question: you are not using two-phase commit anywhere, which is the correct answer. The reserve→charge→deduct sequence with compensations in C2 is a saga, and that is the right pattern for this domain. Do not add an event-sourced write model — the operational cost is not justified at your stage.

H11Gateway1 day

The proxy buffers and rewrites every request and response

api-gateway/src/utils/proxy.ts:96, 103–105, 117

Three problems in one function. reqHeaders.set('content-type', 'application/json') is unconditional, so multipart/form-data uploads to media-service arrive mislabelled and unparseable. The body is JSON.stringify(req.body), which means the gateway must fully parse and re-serialize every payload — and any non-JSON body is destroyed. What's done well

These are above the standard for a codebase at this stage. Keep them, and use them as the pattern when fixing everything above.

Gateway resilience: circuit breaker + bulkhead + retry, correctly layered

Bulkhead outside, breaker inside, retry innermost, each with its own error type and a distinct HTTP status — CIRCUIT_OPEN → 503, BULKHEAD_FULL → 503, timeout → 504. Circuit state is exposed on /health/ready and /internal/metrics. Most teams ship one of these three, badly. The only change needed is the retry-safety fix in C4.

RabbitMQ topology with delay-queue retry, DLQ and Redis idempotency

infrastructure/rabbitmq/ has a dead-letter exchange, per-attempt delay queues dead-lettering back into the main exchange for exponential backoff, a terminal DLQ after max retries, prefetch for backpressure, and a Redis claim/release idempotency guard keyed on eventId. That is a textbook-correct implementation, and it answers the roadmap's exactly-once and poison-pill questions properly. Extend the same idempotency helper to HTTP (C4) rather than writing a second one.

Inventory reservation is the one piece of the checkout path built correctly

Pessimistic locking inside a transaction, availability derived from stock - reserved rather than a mutable counter, TTL-bounded reservation rows with an index on expiresAt for cheap expiry sweeps, and automatic OUT_OF_STOCK propagation. H7 tunes it for hot rows; the design is right.

Refresh token rotation with family-based theft detection

Rotating on every use, and revoking the entire family when an already-rotated token reappears, is the correct pattern and is genuinely uncommon. Tokens are hashed at rest and stored with expiry. Refresh lives in an HttpOnly cookie — the right choice — with a body fallback for mobile clients. Only the bcrypt cost model needs changing (H8).

Search service analyzers are production-grade

Edge-ngram tokenizer with a separate search analyzer (avoiding the classic mistake of ngramming the query too), synonyms, explicit field mappings, vector query building, and a product consumer keeping the index current. This is exactly what the roadmap asks for — it just needs to be on the request path (H5).

Kubernetes manifests are more complete than the application they deploy

Default-deny NetworkPolicy with explicit allows, HPAs on CPU and memory, KEDA ScaledObjects for queue-depth-driven scaling, PodDisruptionBudgets, and separated base/overlay kustomizations. KEDA in particular is the right answer to the roadmap's "1M backlogged messages" question — consumers scale on queue depth, not CPU. Security headers and strict CORS at the gateway are solid too.

Action plan

Ordered by risk removed per day spent. Phase 1 is not optional and is mostly small diffs.

PHASE 1

Close the open doors

2–3 days · do this week

Every item here is exploitable now and none takes more than a day. Nothing else should ship before these land.

  • C1 — stripClientIdentity as the first middleware. One function, four lines. Add a test that asserts a spoofed x-user-roles: ROLE_SUPER_ADMIN gets 401 on /api/v1/admin/users.

  • C7 — remove the hardcoded secret fallbacks; fail startup instead. Drop access tokens to 15 minutes.
  • C8 (partial) — put requireAuth on the three 2FA routes and delete the 'user-123' default today; full MFA enforcement can follow in phase 2.

  • C6 — ownership checks on every checkout, order, payment, return and dispute lookup.

PHASE 3

Make it hold under load

3 weeks · before a marketing push
